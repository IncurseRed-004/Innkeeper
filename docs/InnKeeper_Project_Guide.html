2. Executive summary

InnKeeper is a Django web application with a three-role model:

Role Flag on Login What they do
Customer is_customer = True Browse resorts, view details, book available date slots, see booking history, message resort owners
Owner is_owner = True Register resorts, describe facilities, publish booking slots (date ranges), approve/reject customer bookings, reply to messages
Admin / staff is_staff = True View and delete customers and owners, view all resorts; full access through the stock Django admin

Core domain chain:

Login (auth user) -> Owner -> Resorts -> Facilities -> Schedules -> Booking <- Customer
                                 |
                                 +-> Chat <- Customer

A resort is described by exactly one Facilities record (pool / kitchen / wifi / lawn / balcony booleans). Each facility owns many Schedules, which are the bookable date ranges (from_date … to_date). A customer books a schedule, producing a Booking whose status goes 0 (pending) → 1 (approved) or 2 (rejected).

Pages: a public marketing/landing page with a resort grid, separate customer / owner / admin dashboard shells (Corona Admin theme), plus form pages built with crispy_forms.

State of the project: functional prototype / academic project. It runs end-to-end for the main happy path, but has several real bugs (section 15), no tests, no permissions beyond login_required, and hard-coded development secrets.

6.2 Model reference

Login — custom user (table InnKeeper_app_login)

Inherits AbstractUser, so it also has username, password, first_name, last_name, email, is_staff, is_active, is_superuser, date_joined, last_login, groups, user_permissions.

Field Type Details
is_owner BooleanField default False; set to True during owner registration
is_customer BooleanField default False; set to True during customer registration

Role resolution used everywhere: user.is_customer → customer dashboard, user.is_owner → owner dashboard, user.is_staff → admin dashboard. A user can technically hold more than one flag; the checks are ordered customer → owner → staff.

Field Type Notes

No __str__, no created/updated timestamps, no read/unread state, no message threading.

6.3 Relationship rules and cascade behaviour

Relationship Cardinality On delete
Login → Customer 1:1 deleting the user deletes the customer profile
Login → Owner 1:1 deleting the user deletes the owner profile
Owner → Resorts 1:N deleting an owner deletes all their resorts
Resorts → Facilities 1:N deleting a resort deletes its facilities
Facilities → Schedules 1:N cascade
Schedules → Booking 1:N deleting a slot deletes its bookings
Customer → Booking 1:N cascade
Resorts → Chat 1:N cascade
Customer → Chat 1:N cascade

Consequence: deleting a resort silently removes its facilities, all schedules, all bookings on those schedules, and all chat messages about it.

8. Views — detailed behaviour

8.1 Core and authentication views (views.py)

landing_page(request) — renders Landing.html with no context. Not routed (/ uses list_resorts instead).

list_resorts(request) — the public home page.

facility = Facilities.objects.all()
return render(request, "Landing.html", {"facility": facility})

The template iterates {% for i in facility %} and renders i.resort.name, i.resort.picture.url, i.resort.pricing, i.resort.location, i.resort.address, and links view_details i.id / book_now i.id. So the "resort cards" are really facility rows, and i.id is the Facilities primary key.

dashboard(request) — @login_required, renders the Corona Admin Dashboard.html with hard-coded demo content ("Henry Klein", revenue cards, etc.). Not linked anywhere.

base_landing(request) — renders base_landing.html directly (the shell normally used through {% extends %}). Leftover/debug.

Logout_view(request) — logout(request) then redirect("Login").

Login(request) — accepts GET and POST.

POST: username = POST['uname']; password = POST['pass']
      user = authenticate(username, password)
      if user:
          login(request, user)
          if user.is_customer: -> customer_dashboard
          elif user.is_owner:  -> owner_dashboard
          elif user.is_staff:  -> admin_dashboard
          # (no else: page simply re-renders)
      else: print("Invalid Credentials")
render Login.html

Failures are only printed to the console — no user-visible error message (the messages.info(...) line is commented out).

account_dashboard(request) — @login_required; calls login(request, user) again (redundant) and redirects by role exactly like Login. Used by the "Account Dashboard" nav link on the landing page.

customer_registration(request)

GET : show Login_form() + Customer_Form()
POST: validate both ->
      cust = Login_form.save(commit=False); cust.is_customer = True; cust.save()
      profile = Customer_Form.save(commit=False); profile.user = cust; profile.save()
      redirect("Login")

Both forms are rendered together on customer_page.html via crispy.

owner_registration(request) — identical flow with Owner_Form and is_owner = True; renders owner_page.html. That page has no "register as customer" cross-link (the customer page links to owner registration, but not the reverse).

view_Student(request) — demo: Student.objects.select_related("dept_data").all(), prints name and dept_data.name. Returns None, which Django treats as an error.

8.2 Customer views (customer_views.py)

Every view is @login_required(login_url='Login').

customer_dashboard — renders customer/customer_base.html (dashboard shell with empty content block).

customer_profile — Customer.objects.get(user=request.user) → customer_data; renders the profile card.

edit_customer(request, id) — loads Customer by id, binds Customer_Form on POST, saves, redirects to customer_profile. Note: the id in the URL is not checked against the logged-in user.

view_details(request, facility_id) — Facilities.objects.get(id=facility_id) → details; renders resort_details.html. Because it is login_required, anonymous visitors clicking "Details" on the landing page are bounced to the login screen.

book_now(request, id) — Schedules.objects.filter(facilities=id) → slots; renders book_now.html, which shows each slot's from_date / to_date and either a "Select This Slot" link (when schedule_status == 0) or a disabled "Not available" label.

select_slot(request, id)

GET : customer = Customer.objects.get(user=request.user)
      slot     = Schedules.objects.get(id=id)
      render select_slot.html with {customer, slot}
POST: booking = Booking(); booking.customer = customer; booking.schedule = slot; booking.save()
      slot.schedule_status = 1; slot.save()
      redirect("booking_success")

This is the only place a Booking is created. There is no server-side re-check that the slot is still free, and no uniqueness constraint, so two concurrent submits can both book the slot.

booking_success — static success page with a link back to /.

booking_history — Booking.objects.filter(customer=customer) → history; the template renders resort name, location, dates, price, a status label (pending / Confirmed / rejected) and a "message" link to chat_with booking.schedule.facilities.resort.id.

chat_with(request, id)

resort   = Resorts.objects.get(id=id)          # named "booking" in the code
customer = Customer.objects.get(user=request.user)
POST: Chat(customer=customer, resort=resort, message=POST['message']).save()
      redirect("booking_history")
GET : render customer/chat.html {booking: resort, customer}

view_chat — Chat.objects.filter(customer=customer); table of resort / message / reply ("No reply yet" when empty).

8.3 Owner views (owner_views.py)

owner_dashboard — renders owner/owner_base.html.

owner_profile — Owner.objects.get(user=request.user) → profile card.

edit_owner(request, id) — Owner_Form(instance=...), save, redirect owner_profile.

resort_add

owner = Owner.objects.get(user=request.user)
POST: ResortForm(request.POST, request.FILES)
      resort = form.save(commit=False); resort.owner = owner; resort.save()
      redirect("resort_facilities", resort_id=resort.id)

Files (picture) require the form to be multipart — the template sets enctype="multipart/form-data".

resort_facility(request, resort_id) — Facility_Form (all facility booleans), attaches facilities.resort = resort, saves, redirects to owner_dashboard. (Note: it does not redirect to my_resorts and the form is not pre-filled.)

edit_resort(request, id) — deliberately scoped: Resorts.objects.get(id=id, owner=owner), so an owner cannot edit another owner's resort by URL. Redirects to my_resorts.

edit_facilities(request, resort_id) — Resorts.objects.get(id=resort_id) without the owner filter, then Facilities.objects.get(resort=resort) (raises if there is more than one). Redirects to my_resorts.

delete_resort(request, resort_id) — scoped by owner, deletes, redirects to my_resorts.

my_resorts — Facilities.objects.filter(resort__owner=owner) → facilities; cards show the resort image, name, description, address, location, price, facility checkmarks, and action links (Edit Resort, Edit Facilities, add Schedule, view schedules, Delete Resort).

add_schedules(request, id) — Facilities.objects.get(id=id); Schedule_form (from_date, to_date) → attach facilities, save, redirect my_resorts.

view_schedules(request, id) — Schedules.objects.filter(facilities=id); table with delete.

delete_schedule(request, id) — deletes the Schedules row (and, by cascade, any bookings on it).

booking_status — Booking.objects.filter(schedule__facilities__resort__owner=owner); the template shows customer name, resort, time_data, from/to dates, and either approve/reject buttons (status 0), "approved" (1) or "rejected" (2).

approved(request, id) — booking.status = 1; save() → redirect booking_status. rejected(request, id) — booking.status = 2; save(). Neither verifies that the booking belongs to the requesting owner.

display_message — Chat.objects.filter(resort__owner=owner); table of resort, message and either the existing reply or a "Reply" button.

reply_message(request, id) — on POST sets chat.reply = POST['reply'], saves, redirects to display_message.

All are @login_required — there is no is_staff check, so any authenticated user can use these pages if they know the URL.

10. End-to-end user flows

10.1 Customer registration and login

  1. Visitor → / → "SignUp/LogIn" → /Login.
  2. "Register" → /customer_registration; fills username + password twice + name, phone, email, address → submit.
  3. Server creates Login(is_customer=True) and the linked Customer, then redirects to /Login.
  4. Login with those credentials → is_customer branch → /customer_dashboard.

10.2 Owner onboarding and resort publishing

  1. /owner_registration → creates Login(is_owner=True) + Owner.
  2. Login → /owner_dashboard.
  3. "+ ADD PROPERTIES" → /resort_add → fills resort details + uploads a picture.
  4. Immediately redirected to /resort_facility/<resort.id>/ → ticks facilities → save (lands on /owner_dashboard).
  5. "My resorts" → /add_schedules/<facility.id>/ → adds one or more date ranges.
  6. Slots are now visible to customers; the resort appears on the landing page (it appears as soon as the facilities row exists).

10.3 Customer browsing and booking

  1. / shows every facility card.
  2. "Details" → /view_details/<facility_id> (login required).
  3. "Book Now" → /book_now/<facility_id> — lists slots, hides taken ones.
  4. "Select This Slot" → /select_slot/<schedule_id> — review page.
  5. "Confirm Booking" → creates Booking(status=0), marks the schedule schedule_status=1, → /booking_success.
  6. "Booking History" → sees the row as pending.

10.4 Owner approval

  1. Owner → "resort status" → /booking_status — all bookings across their resorts.
  2. approve → /approved/<booking_id> → status = 1 → back to the list ("approved" text).
  3. reject → /rejected/<booking_id> → status = 2 → list shows "rejected". The slot stays unavailable either way (see 15.4).

10.5 Messaging

  1. Customer → Booking History → "message" (chat_with) → types a message → submit.
  2. Message stored with customer, resort, message (no booking link).
  3. Owner → "messages" → /display_message → sees the message → "Reply" → /reply_message/<chat_id> → types reply → returns to the list showing the reply.
  4. Customer → "chats" → /view_chat → sees message and the owner's reply.

10.6 Administrator

  1. Staff user logs in → /admin_dashboard (or Django admin at /admin/).
  2. Can list/delete customers, list/update/delete owners, view all resorts.
  3. Note: /view_customer → delete currently crashes with NoReverseMatch.

11. Business rules and status codes

Booking.status

Value Meaning Set by
0 Pending (default) select_slot on creation
1 Approved owner_views.approved
2 Rejected owner_views.rejected
anything else Rendered as "rejected" by both templates —

Schedules.schedule_status

Value Meaning Set by
0 Available (default) Schedule_form default
1 Taken / unavailable select_slot after a booking

Not reset when a booking is rejected or when a slot's booking is deleted.

Effective rules

  • A resort is publicly visible as soon as it has a Facilities row.
  • Bookings are created without re-validating availability, so the "taken" state is advisory (template-level only).
  • Any logged-in user can reach any protected page (no role or ownership enforcement except in edit_resort and delete_resort).
  • Prices are free-text strings; there is no currency field, tax, or payment step.

  • Landing/public pages: custom HTML/CSS based on the TemplateMo "Hideaway" real-estate template — Owl Carousel banner, section headings with | separators, Material Design Icons (mdi), Montserrat/Roboto typography, image cards with price badges.

15. Known bugs and inconsistencies

15.1 Broken redirect (crashes)

  • admin_views.delete_customer ends with redirect('admin/view_customer.html') (admin_views.py, line 22). That is a template path, not a URL name → NoReverseMatch every time a customer is deleted from the admin UI. Should be redirect('view_customer').

15.2 Wrong ID passed between my_resorts.html and the views

owner/my_resorts.html builds every action link from facility.id (the Facilities primary key), but the views expect different keys:

Link View expects Template passes Result
edit_resort Resorts id Facilities id wrong record or DoesNotExist
edit_facilities Resorts id Facilities id wrong record or DoesNotExist
delete_resort Resorts id Facilities id may delete the wrong resort
add_schedules Facilities id Facilities id correct
view_schedules Facilities id Facilities id correct

It often appears to work only because the first resort and first facility get the same id (1:1 insertion order); as soon as the two tables diverge this breaks.

15.3 HTML damage in resort_details.html

Stray </head><body> inside {% block content %} and a dangling --> at the end of the file. The "Book Now" button is also inside the facilities loop, so it renders once per facilities row.

15.4 Slot never becomes available again

select_slot sets schedule_status = 1 on booking. Neither rejected nor delete_schedule (reset) nor deleting a booking clears it, so a rejected booking permanently consumes the slot. Also, availability is only checked in the template — select_slot will happily create a second booking for an already-taken slot if the POST is repeated.

15.5 time_data does not record the booking time

Booking.time_data = models.DateField(auto_now=True) — a date, updated on every save. Approving or rejecting a booking overwrites the original booking date, and the UI label "Time Stamp" shows only a date. A DateTimeField(auto_now_add=True) created-at field (plus a separate updated-at) is the correct pattern.

15.6 No authorisation beyond login

  • No is_staff check on admin_views.* — any logged-in customer can open /view_customer, /delete_owner/1, etc.
  • No role check on customer vs owner pages (an owner can open /booking_history).
  • approved / rejected / reply_message / edit_customer accept any id: an owner can approve another owner's booking, and a customer can edit another customer's profile.
  • edit_facilities looks up the resort without the owner filter (unlike edit_resort).

15.7 Destructive actions use GET

delete_customer, delete_owner, delete_resort, delete_schedule, approved and rejected are all plain <a href> GET links, so they are not CSRF-protected and can be triggered by link prefetchers or third-party pages. They should be POST forms with {% csrf_token %}.

15.8 Assumptions that will fail with more data

  • Facilities.objects.get(resort=resort) (edit_facilities) raises MultipleObjectsReturned if a resort has two facilities rows.
  • Customer.objects.get(user=request.user) / Owner.objects.get(...) raise DoesNotExist for a staff user or for a customer/owner whose profile row is missing.
  • Facilities.count is printed for every card in my_resorts (it is the total of the filtered queryset, not a per-resort count).
  • The "No facilities found" list item is never conditional.

15.9 Template and routing leftovers

  • Dashboard.html, Landing.html (as a view), base_landing view, landing_page, view_Student are unused/unrouted or error out.
  • Chat_form is defined but never used (customer/chat.html uses a raw textarea).
  • title tags on Login.html ("Bootstrap demo") and the dashboards ("Corona Admin") are unrebranded.
  • Dead navigation: {% static 'index.html' %} / {% static 'properties.html' %} / {% static 'contact.html' %} links, and the whole unused demo sidebar in the dashboards.
  • Trailing/absent slashes are mixed across routes.
  • Stray C characters after {% endblock %} in five templates.
  • The landing page's contact form posts to / and is discarded.
  • No user-visible login error (invalid credentials are only printed to the console).

15.10 Data-model nits

  • Owner.email is CharField, Customer.email is EmailField.
  • phone is CharField(10) — no country code or validation.
  • pricing is a string; no numeric/decimal type, so it cannot be summed or sorted.
  • Resorts.description uses TextField(max_length=1000) (length not enforced by the DB).
  • Chat has no timestamps or ordering; the owner's view can show replies out of order.
  • Login can hold both is_customer and is_owner; the redirect logic silently prefers customer.
  • dept / Student demo models clutter the schema and the admin.

17. Suggested improvements

Correctness (small, high value)

  1. Fix the delete_customer redirect.
  2. Pass resort ids instead of facility ids (or change the views) in my_resorts.html.
  3. Add status resetting / availability release on rejection and on booking deletion.
  4. Replace time_data with created_at = DateTimeField(auto_now_add=True) and keep a separate updated_at.

  6. Repair resort_details.html markup and move "Book Now" outside the loop.
  7. Show real validation/login errors with the messages framework.

Architecture

  1. Introduce role-checking decorators (@customer_required, @owner_required, @staff_required) and ownership checks on every object-level action.
  2. Convert the destructive GET links into POST forms.
  3. Split settings into base/dev/prod; load secrets from env; add requirements.txt.
  4. Extract the shared dashboard layout into one base template and move the embedded CSS to static/.
  5. Remove dept/Student and the debug views/routes.

Features (if the project is to grow)

  1. Availability model that supports multiple rooms/units per resort instead of one boolean flag.
  2. Prices as DecimalField + currency; booking totals; payments.
  3. Enforce one facilities row per resort with OneToOneField (or support many explicitly).
  4. Chat: timestamps, threads, notifications, unread counts (or replace with a booking-scoped message model).
  5. Search/filter/sort on the landing page; pagination.
  6. Email notifications on booking creation/approval (console backend already configured).
  7. Tests: unit tests for booking state transitions, permission tests per role.
